# 自動跟拍、手動錄影與 SurfTrack

使用者於 **2026-11-14** 再次確認現行為 **CH340G USB-TTL → M0／M1 → 兩顆 180° PWM servo**，
RS485 雲台已收起，見[控制契約](../docs/servo-controller.md)。本頁描述錄影／跟拍策略，
不代表換回後的帶載跟拍已驗收。PWM 角度規劃器可要求回到 `home_deg`；
預設 90° 是程式要求值，不能當作實際軸角或已驗收的「拍攝基準方向」。
現行通道、方向、中立與機械限制須另核對，舊校準不直接沿用。

主要流程以使用者 2026-09-05 確認的規則為準：

1. ARM 後，先看見穩定追浪才開始試拍；相機維持拍攝基準方向，尚不鎖定某個人。
2. 在已看過追浪的人之中，第一位穩定起乘／轉入衝浪的人取得鎖定，開始雲台跟拍。直接出現已起乘／衝浪、未看過追浪的人不啟動此流程。
3. 追浪結束後，若沒有發展成起乘／衝浪，停拍、回拍攝基準方向、正常收尾的純追浪試拍備份到拍攝日期下的 `fail/`。
4. 有效跟拍持續到起乘／衝浪都結束，或鎖定人物失聯逾時；完成影片後接收並上傳私人 Drive。回到追浪也算結束。

「手動開始錄影／結束手動錄影」是額外觸發，沒有暫停功能，可在未 ARM 時使用。手動與自動同時觸發時共用一段影片，兩者都結束才收尾。只要該段曾包含手動觸發，就保留供訓練，不因自動試拍失敗而刪除。STOP 追蹤不會切斷仍啟用的手動錄影；結束手動錄影也不會切斷有效跟拍。已移除背景 10 分鐘分段錄影；開啟介面、相機連線及重連不會自行建立影片。

沿用門檻：追浪 70%、起乘 65%、衝浪 70%；初次追浪與起乘鎖定各要求至少 3 次觀測、0.5 秒。跟拍只調整 `tracking.ride_exit_seconds`，預設 5 秒，同時供人物 ID 保留與有效跟拍退出使用。人物 ID 從最後一次成功配對的偵測起保留 5 秒；跟拍從最後一次同人物有效起乘／衝浪起算，滿 5 秒仍未恢復即收尾影片並回拍攝基準方向。期限內同一人物恢復有效動作就重算 5 秒；漏偵測與低分交替不重置倒數。寬限期間漏偵測維持角度，有人物位置則繼續跟隨。ID 配對仍依框重疊，延長保留時間不保證遮蔽後必定接回同一人。未鎖定試拍中，所有合格動作消失 2 秒就收尾並保留影片；`finished_hold_seconds` 仍為試拍等待及結束冷卻的 2 秒。舊 `lost_grace_seconds` 已退出執行設定；舊 TOML 可載入該欄位，但它不再影響行為。影像／推論失聯的 1.5 秒停止控制保護不隨跟拍寬限放寬。

事件影片是獨立 RTSP 連線的 H.264/H.265 原碼流 MKV，不重新壓縮、不包含聲音、預覽數位裁切或框線。結束會先等待容器完成，再發布到本機接收 API。有效跟拍或手動錄影的 partial 檔保留，不自動上傳。純追浪試拍的 MP4 與中點 JPG 分別存於 `upload/YYMMDD/fail/` 與 `upload/YYMMDD/fail/預覽圖/`。磁碟達停止門檻會結束所有錄影觸發。

Nano 在符合條件的影片收尾後立即通知 `shore-recording-backup.path`。使用者服務在開機時補查一次，備份失敗時，保留原片，兩分鐘後再試。空閒且沒有待傳影片時不輪詢。手動、連續及曾確認起乘或衝浪的完整錄影備份到日期主資料夾。每段完整收尾就排入佇列，背景服務一次處理一段；AI、跟拍或下一段錄影可同時繼續。原片為 H.264 時換封裝，H.265 時使用 Nano 硬體轉出同解析度的 H.264 MP4。收尾失敗的 partial 檔留在卡上。

Drive 的影片位於 `upload/YYMMDD/YYMMDD_NNN.mp4`，同一支的中點 JPEG 位於日期資料夾內的 `預覽圖/YYMMDD_NNN.jpg`。日期依台灣拍攝開始時間，兩個資料夾共用當天的流水號，SQLite 保存已分配的編號。上傳前核對 MKV 的 SHA-256；轉檔檢查解析度、長度與影格封包數，雲端兩個檔案均核對 ID、大小及 MD5 後釋放卡上的影片，保留本機收據。

`deploy/backup-recordings.py` 從 Nano 本機的 `~/.config/shore-tracker/backup-drive.conf` 讀取 `[shore-backup]` 的 `root_folder_id` 與 OAuth 設定，上傳程式沒有設定固定頻寬上限。查看執行紀錄可用 `journalctl --user -u shore-recording-backup.service`。舊式電腦接收器仍可手動啟動：

```sh
python3 deploy/recording-sync.py --ssh jetson --known-hosts ~/.ssh/known_hosts --surf-track ../surf-track
```

執行前請確認 SSH alias 指向目前的 Jetson，並沿用已驗證且保存於 ~/.ssh/known_hosts 的主機金鑰。這個程式不安裝常駐服務；它自行重建掉線的 SSH tunnel。不要同時執行兩份接收器。

之後抽圖標註（既有私人 Drive 必須可用）：

```sh
cd ../surf-track
.venv/bin/python -m surf_track.recordings --prepare-local --sharer Jetson
```

每秒抽 1 張至既有 Store，建立可在 Dataset / Label 選取的資料集，並共用既有 Drive 上傳功能保存影格。依每段錄影 metadata 的 rotation_degrees 處理方向；原始 MKV 保持相機碼流方向。2026-09-09 使用者已手動翻轉相機，本機部署設定改為 0°，實際套用狀態需在目標 Jetson 上另行確認。設定生效後，新錄影會記錄 0°，抽圖不再旋轉；舊錄影原有的 180° metadata 保留，不回溯改寫。已處理影片可重跑而不重複建影格。完成標註後，在既有 Train 頁選 Jetson 分享者與遠端 GPU 主機開始訓練。

同一影片所有影格屬於同一 source_group，不切散到不同 split；預設新增影片為 train。要留一批做驗證／測試，對尚未匯入影片使用 `--split valid` 或 `--split test`。這個功能不會自動開始訓練，也不改模型與舊資料集。

追蹤推論、固定頻率雲台控制與錄影有各自的執行緒。影片下載由獨立 HTTP 請求處理，Google Drive 上傳在電腦上的獨立接收程序依序執行，追蹤不等待上傳結果。下載共用 Jetson 磁碟與網路資源。單一事件錄影器收尾期間，新錄影觸發等待容器／雜湊完成；雲台控制執行緒繼續運作。
